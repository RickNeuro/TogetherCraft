# TogetherCraft — план проекта

Состояние документа: 14 ноября 2026 года. Основная ветка — `main`.

Галочка означает, что функция или механизм присутствует в коде/конфигурации. Для внешней инфраструктуры отдельно указано, требуется ли проверка на работающем сервере.

## Уже реализовано

### Сайт и игровые направления
- [x] Главная страница сообщества с направлениями Minecraft Vanilla, Minecraft Create и Factorio.
- [x] Отдельные страницы игровых миров, галереи, команды и FAQ.
- [x] Галерея отображает изображения из `wwwroot/images/gallery` и поддерживает просмотр изображений. Пользовательская загрузка через интерфейс пока не реализована.
- [x] Карточки миров используют локальные изображения: Minecraft — замшелый булыжник, Create — оригинальная шестерня мода, Factorio — логотип игры. Ассеты скачиваются во время Docker-сборки.
- [x] Factorio представлен как направление сообщества. Сам игровой сервер Factorio и интеграция с ним ещё не запущены.

### Аккаунты и доступ
- [x] Регистрация, авторизация и хранение аккаунтов в PostgreSQL.
- [x] Привязка Minecraft Java-профиля через Microsoft OAuth при настроенной OAuth-конфигурации.
- [x] Заявки на доступ обрабатываются администратором.
- [x] Администратор может одобрять и отклонять заявки, а также управлять ролями.
- [x] Адреса игровых серверов доступны одобренным пользователям для выбранных ими миров.
- [x] Технические статусы и системные метрики доступны только администраторам.
- [ ] Причина отклонения заявки и история решений пока не сохраняются.

### Minecraft и мониторинг
- [x] Для Vanilla и Create предусмотрены отдельные настройки Server List Ping и RCON.
- [x] Реализована серверная логика добавления Minecraft-ника в whitelist выбранного мира при одобрении заявки.
- [x] Реализованы сбор и отображение системных метрик через Prometheus и Node Exporter.
- [x] В коде предусмотрено получение CPU, RAM, диска, температуры и показателей FAN1/FAN3 при наличии соответствующих датчиков.
- [x] RCON используется для whitelist; функции управления запуском/остановкой игровых серверов через сайт нет.

### База данных, CI и деплой
- [x] Docker Compose, первичная настройка и bootstrap схемы PostgreSQL.
- [x] Секреты приложения хранятся в локальном `.env`, а не в репозитории.
- [x] CI выполняет .NET-сборку, проверку Compose, запуск временной PostgreSQL, smoke-тесты и Playwright/Chromium E2E.
- [x] Актуальная версия консолидирована в `main`; изменения проходят через отдельные рабочие ветки и pull request.
- [x] Production-деплой выполняется отдельным GitHub Actions workflow на self-hosted Ubuntu runner после успешного CI для актуального коммита в `main`.
- [x] Перед деплоем создаётся резервная копия PostgreSQL; после сборки и запуска приложение проходит health-check.
- [x] При неудачном health-check предусмотрена попытка отката образа приложения.

## Проверить на реальной инфраструктуре

Наличие реализации в коде не подтверждает доступность внешних серверов, датчиков или публичной сети. Эти пункты закрывать только после практической проверки.

- [ ] Проверить Server List Ping обоих Minecraft-серверов с хоста приложения: адрес, порт, версия и доступность.
- [ ] Проверить реальные RCON-подключения к Vanilla и Create.
- [ ] Провести полный сценарий: регистрация → привязка Minecraft → одобрение администратором → добавление ника в whitelist выбранного мира.
- [ ] Проверить повторное одобрение/добавление ника и обработку уже существующей записи whitelist.
- [ ] Проверить фактические метрики на Ubuntu: CPU, RAM, файловая система и доступность температурных датчиков и FAN1/FAN3. Отсутствующие на оборудовании датчики должны отображаться как недоступные, а не как реальные значения.
- [ ] Проверить публичный HTTPS через Caddy: DNS, домен, доступность портов 80/443, получение и продление сертификата.
- [ ] Сверить адрес Caddy с настройкой `ForwardedHeaders:KnownProxy`. README упоминает адрес `172.30.0.10`, однако текущий Compose не закрепляет этот IP статически, а настройка доверенного прокси не передаётся веб-контейнеру через Compose.
- [ ] Проверить корректное определение исходного IP и HTTPS-схемы за прокси; убедиться, что внутренние сервисы не доступны извне напрямую.
- [ ] Проверить восстановление PostgreSQL из резервной копии `.dump` на отдельной тестовой базе. Создание backup при деплое реализовано, но успешное восстановление нужно проверить отдельно.

## Правила работы

1. Основная ветка проекта — `main`. Не создавать новые ветки без необходимости и согласования; перед работой проверять существующие ветки. Ветки, изменения которых уже полностью влиты в `main`, можно удалять после проверки.
2. Перед изменениями читать этот файл и связанные исходники.
3. Не менять дизайн, конфигурацию игровых серверов и production без отдельной согласованной задачи.
4. На исправляемую ошибку добавлять воспроизводящий тест, если это возможно.
5. Перед объединением изменений должны проходить CI и необходимые проверки конфигурации.
6. После успешного CI для актуального коммита в `main` GitHub Actions автоматически запускает production-деплой на self-hosted Ubuntu runner. Отдельной проверки `DEPLOY_ENABLED=true` в текущем workflow нет.
7. Деплой создаёт резервную копию PostgreSQL, запускает bootstrap, собирает и запускает приложение, затем проверяет health-check. При сбое health-check предусмотрена попытка отката образа приложения; восстановление базы автоматически не выполняется.
8. Не удалять PostgreSQL volumes и не выполнять разрушительные миграции без проверенной резервной копии и плана восстановления.
9. Не считать внешнюю интеграцию проверенной только потому, что код собирается или проходит тесты на временной среде.
