Состояние документа: 14 ноября 2026 года. Основная ветка — `main`.

Галочка означает, что возможность реализована в коде или конфигурации. Она не означает, что внешняя инфраструктура уже проверена на практике.

**Результат этапа:** основные публичные страницы выглядят и работают ожидаемо, а галерея показывает реальные изображения, а не только пустое состояние.

**Результат этапа:** новый участник действительно может зарегистрироваться, получить одобрение и подключиться только к выбранному игровому миру.

## Позже — без блокировки текущей работы

### Публичный HTTPS и домен
Пока TogetherCraft используется по HTTP в локальной сети, это не блокирует текущую разработку. Возвращаться к публичному HTTPS нужно, когда появится домен и бюджет на его использование.

- [ ] Выбрать и настроить публичный домен, проверить DNS.
- [ ] Настроить Caddy как HTTPS reverse proxy и проверить выпуск/продление TLS-сертификата.
- [ ] Сверить адрес Caddy с `ForwardedHeaders:KnownProxy`. README упоминает `172.30.0.10`, но Compose сейчас не закрепляет этот IP и не передаёт настройку доверенного прокси веб-приложению.
- [ ] Проверить исходный IP клиента и HTTPS-схему за прокси.
- [ ] Убедиться, что PostgreSQL, Prometheus, Node Exporter и RCON не доступны напрямую из интернета.

**Для текущей работы:** локальный адрес `http://192.168.0.60:8080` остаётся основным. Настройка Caddy и HTTPS не входит в ближайшие приоритеты.

## Правила работы

1. Основная ветка — `main`. Новые ветки не создавать. Изменения вносить непосредственно в `main`, если владелец проекта не попросил другой порядок.
2. Старые ветки удалять только после проверки, что их уникальные изменения уже присутствуют в `main`. Не удалять ветки с незлитыми коммитами.
3. Перед изменениями читать этот файл и связанные исходники.
4. Не менять дизайн, конфигурацию игровых серверов и production без отдельной согласованной задачи.
5. На исправляемую ошибку добавлять воспроизводящий тест, если это возможно.
6. Перед выкладкой должны проходить CI и необходимые проверки конфигурации.
7. После успешного CI для актуального коммита в `main` GitHub Actions автоматически запускает production-деплой на self-hosted Ubuntu runner. Отдельной проверки `DEPLOY_ENABLED=true` в текущем workflow нет.
8. Деплой создаёт резервную копию PostgreSQL, запускает bootstrap, собирает и запускает приложение, затем проверяет health-check. При сбое health-check предусмотрена попытка отката образа приложения; автоматическое восстановление базы не выполняется.
9. Не удалять PostgreSQL volumes и не выполнять разрушительные миграции без проверенной резервной копии и плана восстановления.
10. Не считать внешнюю интеграцию проверенной только потому, что код собирается или проходит тесты на временной среде.
11. Каждое новое согласованное правило работы с проектом добавлять в этот `ROADMAP.md` до его применения. После фиксации правила следовать ему в дальнейшей работе.
